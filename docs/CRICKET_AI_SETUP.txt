2. HOW A QUESTION IS ANSWERED (ARCHITECTURE)
------------------------------------------------------------------------------------------

  Mobile app
     |  POST /api/v1/ai/ask { question, language, matchId?, deviceId }
     v
  AiController -> AiService
     1. AI_ENABLED?                          no  -> 503 AI_DISABLED
     2. Provider configured and ready?       no  -> 503 AI_NOT_CONFIGURED
     3. Limits (Redis, keyed hashes):  per IP / per device per minute / per device per day
                                             hit -> 429 AI_QUOTA_EXCEEDED
     4. Daily token budget (real providers)  hit -> 503 AI_BUDGET_EXHAUSTED
     5. Concurrency cap per API instance     hit -> 503 AI_BUSY
     6. AiGateway: model <-> tools loop
          - at most 4 model calls per question (the last call gets no tools)
          - at most 4 tool calls per round, 8 s per tool, 6,000 characters per tool result
          - whole question limited by AI_REQUEST_TIMEOUT_MS -> 503 AI_TIMEOUT
          - provider failure                                -> 502 AI_PROVIDER_ERROR
     7. Answer (max 2,000 characters) + sources + disclaimer
     8. Counters only: Redis -> flushed every 5 minutes into MySQL ai_usage_daily

  Tools only READ data through existing services (live scores from Redis, match details,
  history summary tables through fixed Prisma queries). The model never sees SQL, URLs,
  the Latiyal token or the API key, and cannot run code.

  Providers:
    mock               free, deterministic: chooses tools by keywords and answers with
                       English/Hindi templates. Marked "mocked": true in the response.
    openai-compatible  any server with POST {LLM_BASE_URL}/chat/completions and tool
                       calling (Ollama, vLLM, LM Studio, hosted APIs).

6. STEP-BY-STEP: TURNING IT ON
------------------------------------------------------------------------------------------

Local development (safe order):
  1. Use a LOCAL MySQL database, not the production one (see the warning in section 4).
  2. cd backend && npx prisma migrate deploy        (against the local DB only)
  3. npm run history:import -- --dir "C:\Users\gaikw\Downloads\all_csv" --limit 50 --database <local db>
  4. Set AI_ENABLED=true, LLM_PROVIDER=mock and start the API (npm run start:dev).
  5. Ask: curl -X POST http://localhost:3000/api/v1/ai/ask -H "Content-Type: application/json"
          -d "{\"question\":\"What is the score?\",\"deviceId\":\"dev-device-0001\"}"
  6. Open the admin panel: "AI assistant" (counters) and "Identity mapping".

Production (each step is a deliberate decision; stop after any step):
  1. Backup MySQL (mysqldump) and check free disk space.
  2. npx prisma migrate deploy  (applies the 3 additive migrations).
  3. Deploy the new build (npm ci, npx prisma generate, npm run build, admin build).
  4. Turn on the demo assistant first: AI_ENABLED=true, LLM_PROVIDER=mock.
     pm2 reload live-score-api. Check GET /api/v1/ai/status -> "available": true.
  5. Import the archive (section 8), outside match hours.
  6. Admin > Identity mapping: Propose teams, venues, players; review and confirm.
  7. AI_HISTORY_ENABLED=true, reload the API.
  8. Before any real model: update the privacy policy (placeholder, contact, providers),
     choose Ollama (section 7) or a hosted provider, set AI_DAILY_TOKEN_BUDGET > 0.
  9. Mobile app: hide the AI entry while /ai/status says "available": false, show the
     "disclaimer" under every answer, and show "Historical data: Cricsheet
     (cricsheet.org), ODC-By 1.0" when a source starts with "Cricsheet archive:".

Optional nginx change for slow models (repo template deploy/nginx/api.example.com.conf,
apply on the server yourself; it is not applied automatically):
     location /api/v1/ai/ {
         proxy_pass http://live_score_api;
         include /etc/nginx/snippets/live-score-proxy.conf;
         proxy_read_timeout 160s;
         proxy_send_timeout 160s;
     }
  Then AI_REQUEST_TIMEOUT_MS can go up to ~150000.

7. FREE LOCAL MODEL WITH OLLAMA (OPTIONAL, BUDGET 0)
------------------------------------------------------------------------------------------

Ollama exposes an OpenAI-compatible API at http://127.0.0.1:11434/v1, so no code change
and no API key is needed.

  Install (Ubuntu):  curl -fsSL https://ollama.com/install.sh | sh
  Pull a model with tool calling, e.g.:  ollama pull qwen2.5:7b-instruct
                                 or:     ollama pull llama3.1:8b
  Settings:
     AI_ENABLED=true
     LLM_PROVIDER=openai-compatible
     LLM_BASE_URL=http://127.0.0.1:11434/v1
     LLM_MODEL=qwen2.5:7b-instruct
     AI_DAILY_TOKEN_BUDGET=2000000        (required > 0 even for local models)
     LLM_TIMEOUT_MS=60000
     AI_REQUEST_TIMEOUT_MS=150000         (only with the nginx change in section 6)
     AI_MAX_CONCURRENT=1 or 2             (CPU inference is slow)

  Sizing: a 7-8B model (4-bit) needs about 6-8 GB RAM. On CPU only, one answer with tool
  rounds can take 10-60 seconds; a GPU makes it a few seconds. Keep it on the same server
  (localhost) or a private host reached over https.

  Hosted provider instead: LLM_BASE_URL=https://..., LLM_API_KEY=..., LLM_MODEL=...,
  set LLM_COST_PER_1K_* and a budget. Never enable it before the privacy policy update.

  After reload, GET /api/v1/ai/status should be available and Ask responses must show
  mocked:false (admin Match AI panel). If mocked stays true, LLM_PROVIDER is still mock.

8. CRICSHEET HISTORY IMPORT (npm run history:import)
------------------------------------------------------------------------------------------

Source: Cricsheet classic CSV files (cricsheet.org), e.g. C:\Users\gaikw\Downloads\all_csv

  npm run history:import -- --help
  npm run history:import -- --dir <folder> --dry-run                    parse only, no DB
  npm run history:import -- --dir <folder> --limit 50 --database <db>   small trial
  npm run history:import -- --dir <folder> --files 1000851.csv,1023647.csv --database <db>
  npm run history:import -- --dir <folder> --database <db> --confirm-full-import
  npm run history:import -- --resume --dir <folder> --database <db>
  npm run history:import -- --update-changed --dir <folder> --database <db>
  npm run history:import -- --aggregates-only --database <db>
  npm run history:import -- --rollback-run <id> --database <db>

  Other flags: --no-aggregates, --concurrency <n> (default 2),
  --max-files-per-second <n>, --batch-size <n> (default 5000), --report <file.json>

Safety guards (the CLI refuses to write unless all apply):
  --database <name>          must equal the database name in the URL
  --allow-remote-database    required if the host is not localhost
  --allow-production         required when NODE_ENV=production
  --confirm-full-import      required without --limit / --files
  The CLI prints only host:port/database, never the password. Ctrl+C stops after the files
  in progress; continue later with --resume.

Behaviour:
  - One transaction per match. Re-running skips unchanged files (same SHA-256 and parser
    version). Changed files are reported and only replaced with --update-changed.
  - Files with errors are QUARANTINED (listed with reasons), the run continues.
  - Summary tables are rebuilt at the end (super overs excluded).
  - --rollback-run deletes the matches a run wrote; it cannot restore an older version
    replaced by --update-changed.
  - Full archive: about 23,000 files and 11.7 million deliveries; plan several GB of MySQL
    space; a dry run took about 3 minutes, a real import will take much longer.

9. IDENTITY MAPPING
------------------------------------------------------------------------------------------

Why: Latiyal (live) and Cricsheet (history) use different ids and spellings
("Rohit Sharma" vs "RG Sharma").

How proposals are made (nothing is ever auto-confirmed):
  Players  exact name = 90; same surname + compatible initials = 60;
           +10 if the person played for the national team named in the player's country;
           ties lower confidence by 20; more than 3 equal candidates = skipped (ambiguous).
  Teams    exact name match; "India Women" / "India W" = women's team (gender female);
           one match = 90, several = 50 each.
  Venues   same ground name (", City" suffix removed) and same or missing city;
           90 with matching city, 75 otherwise; never across different cities.

Rules on CONFIRM (409 CONFLICT otherwise):
  - a Latiyal player <-> exactly one Cricsheet person, and the reverse;
  - a Cricsheet team (per gender) or venue belongs to one live team / venue
    (one live team may cover several Cricsheet names, e.g. renamed franchises).
Re-running "Propose" adds new rows and refreshes PROPOSED rows only; CONFIRMED and
REJECTED rows are never changed. "Reopen" sets a row back to PROPOSED.

The AI uses CONFIRMED rows first. Without them: players are found by name in the archive
(several matches -> the AI asks which one), teams by exact name, venues by name + city.

11. TOOLS THE AI CAN USE (all read-only, arguments validated before use)
------------------------------------------------------------------------------------------

Always available:
  get_live_matches          matches in play now
  get_match                 score, status, batsmen, bowler, target, required rate
  get_scorecard             full scorecard
  get_recent_commentary     latest balls (limit 1-30, default 12); may not include
                            every delivery
  calculate_required_rate   arithmetic only (e.g. 100 runs in 6 overs = 16.67 per over)
  get_win_probability       Latiyal matchProbHistory latest point, else liveMatch
                            prediction fields when present (estimate only)
  project_score             projected innings total from current RR × overs left
                            (limited overs; arithmetic estimate, not a guarantee)
  project_next_overs        runs in next N overs: blends live RR, recent overs,
                            batter@venue / bowler economy / batter-vs-bowler when
                            identity maps exist; Latiyal win%/prediction as context

Only with AI_HISTORY_ENABLED=true (Cricsheet archive):
  get_player_history        batting/bowling by format and team type, averages, strike
                            rate, economy, best; optional event + format + gender filter
                            (battingByEvent / bowlingByEvent); candidates if ambiguous
                            For IPL use event "Indian Premier League" (defaults T20)
  get_event_results         tournament/event matches and winner (Final preferred) by
                            event fragment, year, format, gender — archive only
                            (IPL title / who won IPL {year})
  get_event_leaders         most runs (Orange Cap), most wickets (Purple Cap),
                            most runs conceded, most sixes — by event + year
  get_event_standings       points table + computed NRR (archive estimate)
  get_event_awards          most Player of the Match (POT proxy)
  get_event_phase_stats     powerplay/middle/death with won/lost/playoffs filters
                            (team or batter); home/away not supported
  get_event_team_matches    A vs B results/scores/margins in an event/year
  get_event_extremes        highest/lowest totals, biggest margins
  get_head_to_head          results between two teams (by matchId or names), per format
  get_venue_history         matches, average first-innings score, bat-first vs chasing
                            wins, highest and lowest totals (all spellings combined)
  get_team_phase_stats      career team phases (prefer get_event_phase_stats for IPL)

Formats: T20 = T20 + IT20, ODI = ODI + ODM, Test = Test + MDM (domestic included; each
row says which). Every history result carries the coverage note.

12. LIMITS AND SAFETY
------------------------------------------------------------------------------------------

  - Off by default; a real provider is refused without URL, model, key (non-local) and a
    token budget > 0. Unknown cost is never treated as free.
  - Provider URL comes only from configuration; https or localhost http only; redirects
    are refused; the provider's error body is never returned or logged.
  - Per device 5/min and 50/day, per IP 20/min (Redis, shared by all instances), plus
    the global per-IP REST rate limit.
  - Concurrency cap per API instance; daily token budget across instances (approximate
    when many questions finish at the same moment).
  - Max 4 model calls, 4 tools per round, 8 s per tool, 6,000 chars per tool result,
    2,000 chars per answer, AI_REQUEST_TIMEOUT_MS per question.
  - Tool results are treated as data; the prompt tells the model to ignore instructions
    inside them. Cricket-only, no betting advice, no certain predictions.
  - No SQL is built from model or user text; tools call fixed Prisma queries/services.
  - Latiyal polling is unchanged; the AI reads cached live data only.


------------------------------------------------------------------------------------------
13. PRIVACY: WHAT IS STORED AND WHAT IS NOT
------------------------------------------------------------------------------------------

  NOT stored anywhere: question text, answer text, conversations, prompts, tool
  transcripts, device ids, IP addresses, FCM tokens.

  Redis (short-lived): limit counters keyed by an HMAC of the device id / IP
     (keys cricket:v1:ai:quota:..., expire after 2 minutes or 2 days),
     daily token total (ai:tokens:<day>), usage counters (ai:usage:..., 8 days).
  MySQL: ai_usage_daily = per day/provider/model counts: requests, answered, refusals,
     errors, timeouts, tokens, tool calls, English/Hindi, total latency, estimated cost.
  Logs: one "[ai-ask]" line per question with outcome, provider, language, tool names,
     token counts and latency only. Tests fail if a question, device id, IP or key shows
     up in logs, Redis or the database.
  There is deliberately no admin conversation viewer.

  When a hosted provider is used, the question and the relevant cricket data are sent to
  it (never the device id or IP). The privacy policy section 14 says this.

------------------------------------------------------------------------------------------
16. TROUBLESHOOTING
------------------------------------------------------------------------------------------

  /ai/status available=false   AI_ENABLED is false, or the provider is not ready. The
                               admin AI page shows the exact reason.
  AI_NOT_CONFIGURED            non-mock provider without valid https/localhost URL, model,
                               key, or with AI_DAILY_TOKEN_BUDGET=0.
  AI_BUDGET_EXHAUSTED          daily token budget used up (resets at 00:00 UTC).
  AI_BUSY                      too many questions in progress, or Redis is down.
  AI_TIMEOUT / nginx 504       model too slow: raise LLM_TIMEOUT_MS and
                               AI_REQUEST_TIMEOUT_MS together with the nginx timeout
                               (section 6), lower AI_MAX_CONCURRENT, or use a smaller model.
  AI_PROVIDER_ERROR            provider returned an error (bad key, model name, server
                               down). Check the provider; the API logs only the status.
  History answers "not in the  migration/import missing, AI_HISTORY_ENABLED=false, or the
  archive / not linked"        team/venue is not mapped and its name differs; map it in
                               Identity mapping.
  Wrong player picked          reject the mapping in Identity mapping and add the right one.
  Import refuses to write      add the guard flags printed in the message (section 8).


------------------------------------------------------------------------------------------
17. KNOWN LIMITATIONS AND RISKS
------------------------------------------------------------------------------------------

  - The local development .env points at the production MySQL server.
  - No local MySQL/Docker was available, so the importer has never written to a real
    database; the MySQL integration tests are written but were skipped.
  - matchProbHistory payloads vary; get_win_probability parses common shapes and returns
    unavailable when the feed is empty or unrecognised. playerInfo / matchInfo still have
    no dedicated AI tools.
  - Commentary is not proven to contain every delivery; the tool says so.
  - The concurrency cap is per API instance; the token budget can be slightly exceeded
    when several questions finish together.
  - Indexes on hist_deliveries (batter/bowler + match) are not benchmarked on full data.
  - Cricsheet coverage is incomplete (not every match ever played); answers say
    "Cricsheet archive" and never "official career totals". Event names differ across
    editions (e.g. "World Cup" vs "ICC Cricket World Cup"); filters use LIKE + format.
  - The mock provider understands simple keyword questions only.
