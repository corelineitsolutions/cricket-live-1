Cricket Live API — test endpoints
Run these on the Ubuntu server. Base URL is the machine itself.

BASE=http://127.0.0.1:3000
ADMIN_PANEL=http://127.0.0.1:3100
Swagger (browser on the server, or tunnel): http://127.0.0.1:3000/api/docs

A healthy JSON body looks like: {"success":true,"data":...}
Replace MATCH_ID with a matchId from /matches/live or /matches.
Replace TOKEN with the accessToken from admin login.

11. Cricket data feeds — every Latiyal endpoint (no login)
List of all 51 feeds with their parameters and refresh period:
curl -sS http://127.0.0.1:3000/api/v1/feeds

Every feed answers {"success":true,"data":{"endpoint","params","data","message","updatedAt","stale"}}.
data.data is the Latiyal "data" payload unchanged. data.data is null (with data.message) when Latiyal
has nothing for those ids. Parameter names are the Latiyal ones. The ids below are the examples from the
Latiyal Postman collection; replace them with real ids (match_id from liveMatchList/homeList etc.).
Responses are cached per feed (1 s for liveMatch, 2 s commentary, 15 s scorecard, up to 24 h for
reference data), so the app can call these as often as it likes.

12. Delay check: is our server behind Latiyal? (run on the server while a match is live)
cd /home/cricket-live-1/backend
npm run latiyal:delay                       first live match, every 1 s for 2 minutes
npm run latiyal:delay -- 5484               a specific Latiyal match id
npm run latiyal:delay -- 5484 --duration 600 --interval 1000
Each line shows the score from Latiyal directly (https://api.latiyalinfotech.com/apiv5/liveMatch),
from our /api/v1/matches/{id} (what the app and socket get) and from /api/v1/feeds/liveMatch.
SAME = our server matches Latiyal. When a new ball appears it prints
"... reached server +X s after Latiyal". The summary gives the average and maximum delay.
0-1 s means no delay on our side. If Latiyal itself is behind TV, every column will be behind together.
